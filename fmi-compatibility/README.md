# Jaxonomy — FMI compatibility

How [Jaxonomy](https://py.jaxonomy.com/) has validated its FMI support, which
tools it has been tested against, and where the limits are. Everything here is
regenerated by [`generate.py`](generate.py) and re-checked by the
`fmu-interop` job in CI on every push, so the page cannot silently drift from
the code.

**Version:** Jaxonomy 3.3.0 · **Interfaces:** FMI 2.0 / 3.0 co-simulation and
model-exchange **import**, FMI 2.0 co-simulation **export**.

## Read this before downloading an FMU

Jaxonomy's exported FMUs are **tool-coupled**. The slave executes as Python,
so the importing side needs a Python environment with Jaxonomy installed:

```
pip install "jaxonomy[fmu]"
```

They are not self-contained binaries, and the bundled platform binaries are
**x86-64** (`linux64`, `win64`). If you are importing into a C/C++ master, see
[Exported FMUs in a non-Python master](#exported-fmus-in-a-non-python-master)
— there is a build step, and without it the FMU will not load *even though
every FMI validator passes it*.

| Model | What it exercises |
|---|---|
| [SpringDamper](SpringDamper/) | Continuous states, one real input, one real output |
| [PIController](PIController/) | Sampled/discrete dynamics, two real inputs |
| [BouncingBall](BouncingBall/) | A zero-crossing event and a state reset across the boundary, no inputs |
| [Feedthrough](Feedthrough/) | Multiple outputs from one input; direct feedthrough |
| [RCNetwork](RCNetwork/) | An acausal DAE compiled through index reduction |
| [MixedTypes](MixedTypes/) | Integer, Boolean and String FMI variables alongside Real |
| [VectorIO](VectorIO/) | Array-valued variables, flattened to `name[i]` |
| [Parameterized](Parameterized/) | FMI parameters — including an initial state — applied at initialization |
| [Thermostat](Thermostat/) | Two-sided hysteresis: mode state plus continuous state |
| [StiffChemical](StiffChemical/) | Stiff kinetics; an implicit BDF solver re-entered every `doStep` |
| [DCMotor](DCMotor/) | Cross-domain acausal (electrical + rotational) behind a causal input |
| [ONNXPolicy](ONNXPolicy/) | A neural policy in the loop, evaluated inside the FMU |
| [UnitsAnnotated](UnitsAnnotated/) | Unit-annotated ports — and what the FMI boundary drops |

Each directory holds the `.fmu`, `_ref.csv`, `_ref.opt`, `_in.csv` where the
model has inputs, a `Readme.txt`, and the model source.

The reference solution is produced by driving the very FMU published here, so
it is what an importer should reproduce rather than a separately-derived
idealization. `_ref.opt` records the options used.

### How each reference was checked

Every reference is verified against a solution derived independently of
Jaxonomy, not merely inspected for plausibility. The references are produced by
driving the FMUs, so that step alone would confirm nothing: a model that is
wrong in-process stays wrong through the FMI boundary and still looks
plausible. [`verify.py`](verify.py) re-derives each trajectory a second way and
exits non-zero on disagreement; the figures below are its output.

| Model | Independent check | Agreement |
|---|---|---|
| SpringDamper | `python-control`, ZOH-discretised to match the hold | 5.1e-10 |
| PIController | Analytic discrete PI recurrence | 5.0e-10 |
| BouncingBall | Analytic free flight; apex ratio against e² | 1.7e-16 first arc; apex ratio 0.489–0.491 vs 0.49 |
| Feedthrough | Analytic (`y = u`, `y = 2u`) | exact / 4e-10 |
| RCNetwork | Analytic charging curve, 1 − e⁻¹ at t = RC | 3.4e-6 |
| MixedTypes | Analytic, per variable and per type | 4e-10 |
| VectorIO | Analytic (`2·[1,2,3]`, sum 12) | exact |
| Parameterized | Analytic `x₀·e^(−kt)` with the parameters set at init | 4.8e-10 |
| Thermostat | Analytic exponential segments; switching-interval durations | 5.0e-9 rise; band held to [49.001, 51.000] |
| StiffChemical | SciPy `solve_ivp` (Radau), plus exact mass conservation | 6.9e-8 rel; \|Σy − 1\| < 1e-10 |
| DCMotor | `python-control` state-space solution of the same equations | 6.0e-7 rel (speed), 1.9e-6 (current) |
| ONNXPolicy | Exact per-interval ZOH integration against the ONNX weights | 3.4e-8 |
| UnitsAnnotated | Analytic tank fill `q·R·(1 − e^(−t/AR))` | 5.0e-10 |

Reading the reference against an input signal: FMI co-simulation holds inputs
constant across a step, so the output recorded at *t*ₖ₊₁ is the response to the
input applied at *t*ₖ. `Feedthrough` and `MixedTypes` both show that one-step
offset exactly.

`BouncingBall` stops at t = 2.55 s rather than the requested 10 s: the
bounces accumulate (Zeno), and the run cannot advance past it. `_ref.opt`
records the stop time actually reached, so the reference and the options
agree.

`MixedTypes` needs a Jaxonomy newer than 3.3.0 on the importing side: 3.3.0
registers every variable as Real, so its slave would contradict the Integer
and Boolean declarations in this FMU's `modelDescription.xml`.

`ONNXPolicy` additionally needs `onnx` and `jaxonnxruntime` in the importing
environment; the `.onnx` itself rides inside the FMU's `resources/`.

## Export: which tools have run our FMUs

| Tool | Version | Role | Result |
|---|---|---|---|
| `fmpy.validate_fmu` | 0.3.x | Validator | Zero findings (CI gate on every generated FMU) |
| INTO-CPS VDMCheck | 1.1.3 | Validator | Passes (CI gate) |
| `fmusim validate` | 0.6.0 | Validator | Clean — ZIP archive, model description, build description |
| FMPy | 0.3.x | Importing master | Instantiates, steps, round-trips against the in-process model |
| Jaxonomy `ModelicaFMU` | 3.3.0 | Importing master | Round-trips |
| **fmusim** | 0.6.0 | **Importing master, no Python in the process** | Instantiates and steps all 13 exported FMUs, including the Integer/Boolean/String and array-valued ones. Eleven need nothing but the wrapper below; `MixedTypes` additionally needs a post-3.3.0 Jaxonomy visible to the embedded interpreter and `ONNXPolicy` needs `onnx` and `jaxonnxruntime`, as noted above. driven by a CSV input it tracks the resonant response to within 0.50% of an independent OpenModelica solution of the same equations |

**Not tested, and one known refusal.** OpenModelica's importer accepts model
exchange only and rejects every co-simulation FMU — including ones
OpenModelica itself exported — so it cannot host a Jaxonomy export at all.
Dymola, Simulink, CarMaker and dSPACE are untested; we make no claim about
them.

### Exported FMUs in a non-Python master

The wrapper PythonFMU ships links no libpython, so a C/C++ master fails at
`dlopen` with `undefined symbol: _Py_NoneStruct`. Every static validator still
reports such an FMU as clean, because they read `modelDescription.xml` and
never load the binary.

[`../scripts/build_pythonfmu_wrapper.sh`](../scripts/build_pythonfmu_wrapper.sh)
builds a wrapper for the host that links libpython, promotes it to global
scope so numpy's C extensions resolve under an `RTLD_LOCAL` master, and skips
a `Py_Finalize` that otherwise segfaults on `fmi2Terminate`. With it, fmusim
runs the FMUs above. `jaxonomy.library.fmu_export.wrapper_diagnostics()`
reports what is installed, and `build_fmu` warns when it would emit an FMU
that cannot load.

## Import: which FMUs we have run

| Source | Version | Interface | FMI | Result |
|---|---|---|---|---|
| FMI Reference FMUs | v0.0.39 | Co-simulation | 2.0, 3.0 | BouncingBall, VanDerPol, Dahlquist, Stair, StateSpace, Feedthrough — CI gate |
| FMI Reference FMUs | v0.0.39 | Model exchange | 2.0, 3.0 | Dahlquist matches the analytic `exp(-t)` to 1.5e-7; VanDerPol holds its limit cycle; BouncingBall's event indicator drives zero-crossing localization and the FMU's event iteration — CI gate |
| OpenModelica | 1.27.0 | Co-simulation | 2.0 | Imported and closed in a loop; agreement with OpenModelica's own solution is first-order in the communication step (4.0e-2 m at `dt=0.01`, 3.9e-3 m at `dt=0.001`) |
| OpenModelica | 1.27.0 | Model exchange | 2.0 | **5.4e-8 m** against the same reference — the error tracks solver tolerance, not a communication step |
| Jaxonomy | 3.3.0 | Co-simulation | 2.0 | Round-trip of our own exports |

The model-exchange row is the reason to prefer it where a tool offers both:
co-simulation holds inputs constant across each step, while model exchange
hands the derivatives to Jaxonomy's solver and turns FMI event indicators into
zero-crossings.

## Known gaps

- **No model-exchange export**, no FMI 3.0 scheduled execution, no FMI 1.0.
- **Exports are co-simulation and tool-coupled**; there is no self-contained
  or source-code FMU export.
- **Bundled platform binaries are x86-64 only.** On aarch64 the build script
  produces a working wrapper for the host, but the published FMUs above carry
  x86-64 binaries.
- **`BouncingBall` terminates on Zeno accumulation** at t = 2.55 s.
- Gradients do not cross the FMI boundary in either direction.
- **Units do not cross the boundary.** Jaxonomy checks `Unit`-annotated ports
  at connect time, but an exported FMU carries no `unit` attribute and no
  `UnitDefinitions`: the PythonFMU wrapper emits neither. Jaxonomy's `Unit`
  (seven SI exponents, scale, offset) maps cleanly onto FMI's `BaseUnit`, so
  this is unimplemented rather than blocked. [`UnitsAnnotated`](UnitsAnnotated/)
  is the worked demonstration.
- **An exported vector *input* port collapses to one scalar variable.** An
  exported input carries no shape until something feeds it, so the slave
  registers a single Real where the model wants *n*. Vector *outputs* and
  vector `Constant` inputs both flatten correctly — drive array inputs from a
  `Constant`, as [`VectorIO`](VectorIO/) does.
- **String variables carry metadata only.** Jaxonomy has no string-valued
  signal, so `EXPOSE_STRINGS` variables round-trip across the boundary
  without reaching the diagram.

The authoritative, continuously-updated list is
[`../KNOWN_GAPS.md`](../KNOWN_GAPS.md) under *FMU support*.

## Reproducing this

```bash
pip install "jaxonomy[fmu]" control onnx jaxonnxruntime
bash scripts/build_pythonfmu_wrapper.sh
python fmi-compatibility/generate.py
python fmi-compatibility/verify.py
```

`control` backs the DCMotor cross-check and `onnx`/`jaxonnxruntime` build and
run the ONNXPolicy model; neither is part of the `[fmu]` extra.

The import side is reproduced by the `fmu-interop` CI job, which builds the
Reference FMUs and fmusim from pinned versions and runs both directions.

Problems with any of this are worth an
[issue](https://github.com/machinavitalis/jaxonomy/issues).
